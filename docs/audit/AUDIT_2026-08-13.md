# Security and code-health sweep — 2026-08-13 (v0.42.0)

A second pass over the whole app, ten days after the [2026-08-03 audit](SECURITY_AUDIT.md) and
covering the three features shipped since it (refunds, the monthly donor's stop link, per-appeal
Stripe accounts). Scope: every server route, the data layer, the web bundle, the container, the
dependency tree, the git history, and all fourteen markdown files.

**Headline:** one real donor-facing defect, four small ones, and no new vulnerability. The finding
that matters is that a feature shipped three weeks ago has never once worked.

---

## Fixed in this sweep

### D-2026-0813-1 — the branded receipt could never be sent (High, correctness)

`receipt` is decided once at intent, and going "branded" **suppresses Stripe's own receipt** in
favour of ours. That decision was gated on `emailStatus() === 'ok'`.

`'ok'` is written in exactly one place: inside `fabricEmail`, on a successful send. And the only
sends that happened were ones the gate had already permitted. **A closed loop.** On a fresh container
the status starts at `'unknown'`, so no one-time donation was ever marked as owing a branded
receipt, so `fabricEmail` was never called, so the status never moved.

The blast radius is the whole life of the feature: from **v0.29.0** (2026-07-20), when branded
receipts shipped, until **v0.42.0-dev.1** (2026-08-12), *no masjid could ever have sent one for a
one-time donation*, however carefully they configured it. It was invisible because the fallback is
silent and correct — Stripe's own receipt went out instead, so donors were receipted and nothing
looked broken. Only the branding was missing, and only the masjid would have noticed. The status
being in-memory made it worse: even the two paths that could break the loop (a refund notice, or the
monthly setup letter added yesterday) lost it again on the next restart — and the app restarts
itself whenever remote access changes in OpenMasjidOS.

**Fix.** The gate is now `emailLikelyAvailable()`: try unless we hold *positive* evidence that email
cannot work (`not_configured`, or no Fabric at all). "Never tried", a timeout, a 500 and a rate limit
are all "we don't know", and the honest answer to not knowing is to try. The status is persisted to
the data volume (`store.getEmailStatus` / `setEmailStatus`, fed from `fabric.ts` through a small
sink) so a negative is learned once rather than every boot.

**The new failure mode is bounded and self-healing, which is why this direction is the right one.**
If email genuinely is unconfigured, the first donation after an admin enables receipts loses its
receipt — we suppressed Stripe's, ours failed. The platform then tells us `not_configured`, that is
written down, and every subsequent donation falls back to Stripe's receipt. One donation, once,
against every donation, for ever.

Written up in [`../ARCHITECTURE.md`](../ARCHITECTURE.md) → *The receipt gate was a closed loop*, and
pinned as a `CLAUDE.md` §13 invariant so it cannot be "tightened" back.

### D-2026-0813-2 — a malformed JSON body returned 500, with the parser's own message (Low)

The app replaces Fastify's JSON parser to keep the raw bytes for Stripe webhook signature
verification, and on a parse failure passed the bare `SyntaxError` through. Every route in the app
therefore answered a body **the client had sent wrong** as a server fault.

Worth recording precisely, because the obvious fix is wrong twice over: **a content-type-parser
error never reaches `setErrorHandler` at all.** Fastify v5 serialises it itself, so the app's error
envelope and its "never leak a raw message" rule did not apply — the response was
`500 {"statusCode":500,"error":"Internal Server Error","message":"Unexpected token n in JSON…"}`,
i.e. the parser's own text on the wire, which is exactly what that handler exists to prevent.
Attaching `statusCode: 400` to the error corrects the number and nothing else: Fastify still uses its
own serialiser, putting a bare `"error":"Bad Request"` in the field
[`web/src/api.ts`](../../web/src/api.ts) reads to decide what to show a person.

Fixed by flagging the request in the parser and refusing it in a `preValidation` hook, which is on
the normal reply path — so it gets the app's envelope, a 400, and the same friendly sentence every
other unreadable request gets. It is deliberately **not** swallowed as "no body" and left to the
routes' own zod validation: `RefundBody.safeParse(req.body ?? {})` succeeds on an empty object and
means *refund everything left*, so unreadable JSON would have become a full refund.

Verified end to end against a booted server, including that the webhook's raw body is still intact
and that `requireAdmin` still fires on the routes behind it.

### D-2026-0813-3 — stop-link tokens reached the database without a shape check (Low)

`looksLikePlanToken` exists, is tested, and its own doc comment says it is the check to run "before
any lookup, so a junk path can be refused without touching the database". It was never wired into
`resolvePlanToken`. The route is unauthenticated and is linked from donor email, so it is exactly
the one that attracts link scanners. Now checked before the query. No behaviour change for a real
token; every failure stays the same uniform 404.

### D-2026-0813-4 — deleting a Stripe account gave the wrong reason (Low, UX)

`deleteStripeAccount` distinguishes `in-use` (a campaign points at it) from `has-payments` (money was
taken through it), and the route reported both as *"A campaign uses this account. Reassign or delete
those campaigns first."* An admin hitting the second case is sent looking for campaigns that do not
exist. They now get the real reason — removing it would strand those payments' refunds and leave any
monthly plans on it unstoppable — which is also the one that can never be resolved by editing a
campaign.

### D-2026-0813-5 — the minimum-donation floor was on the wrong scale (Low)

```ts
const floor = currencyDecimals(currency) === 0 ? 50 : 50;   // both branches identical
```

Dead code with a real edge: in the five three-decimal currencies (BHD, JOD, KWD, OMR, TND) 50 minor
units is 0.050 — about 13 US cents, below anything Stripe will accept — so the app's own floor never
bound and the donor met a Stripe decline instead of a sentence. Now `500` for those, unchanged
elsewhere. Same family as DONATIONS-001; the 2026-08-03 fix corrected the conversion but not this.

## Checked, and no change needed

### `@fastify/static` ≤ 10.1.1 — four High advisories, none reachable here

Re-verified rather than re-inherited from the last audit. All four (directory-listing path traversal,
route-guard bypass via encoded separators, authorization bypass via non-canonical paths, route-guard
bypass via traversal) depend on a configuration this app does not have:

- both registrations pass `index: false`, and neither passes `list: true`;
- **neither static route has any guard or authorization hook** — the only global hook is the
  response-header one, and `requireAdmin` is attached per-route to `/api/admin/*`, never to static;
- both roots hold content that is already public by design (admin-uploaded campaign images at
  `/uploads/`, and the built web app).

There is no v8 patch — the fix is 8.x → 10.1.3, two majors. That belongs in a change someone can
start a container against, not in a release. **Still open**, with the same reasoning as
[`ACTION_REQUIRED.md`](ACTION_REQUIRED.md) §4g. The web app's production tree has zero advisories.

### Everything else that was looked for and not found

| Checked | Result |
|---|---|
| SQL injection | One interpolation in 1,500 lines of data layer — `PRAGMA table_info(${table})` — fed only by hardcoded literals in the constructor. Every other statement is parameterised. |
| XSS | No `dangerouslySetInnerHTML`, no `innerHTML`, no `eval`, no `new Function`, no `document.write` anywhere in the tree. Release notes and all campaign text render as React nodes; the receipt email is escaped server-side and unit-tested. |
| Secrets reaching the browser | The web bundle never *receives* `secretKey` or `webhookSecret` — only sends them on the admin's own save. `publicAccount` / `publicStripeStatus` return the publishable key and booleans. |
| Secrets in logs | The logger takes messages only; every `catch` logs `err.message`, never the error object. The tunnel deliberately never logs cloudflared's raw output. |
| Credentials in git history | Re-scanned. Still none — consistent with the 2026-08-03 result. |
| `target="_blank"` | Every one carries `rel`. |
| Open redirect | `base.ts` only prefixes paths the app constructs; no user-supplied redirect target anywhere. |
| CSV injection | `csvCell` still on every exported cell, still locked by `csv.test.ts`. |
| SSRF on outbound calls | Every Fabric and Students call sets `redirect: 'error'` and an `AbortController` timeout; the base URL comes from platform-injected env, never a request. |
| Rate limiting | Login (exponential lockout), donation intent, monthly sign-up, tuition lookup, the webhook, the donor stop link, and platform calls — all keyed on the real TCP peer, never a spoofable header. |
| Uploads | Raster only; SVG deliberately refused (it can carry script and is served from our own origin). Server-chosen name and extension, 5 MiB cap, `nosniff` on every response. |

### A documentation finding worth calling a finding

[`RESTORE_SSO_FIX.md`](../RESTORE_SSO_FIX.md) instructed the reader, in its own numbered fix list, to
*"drop the `if (ssoConfigured()) return 403` in `/api/setup`"*. Following that literally would
reintroduce a **permanent unauthenticated takeover**: under SSO the local admin is never set, so
`hasAdmin()` stays false for ever and an unguarded setup route never closes. The shipped code does
the narrower, correct thing (refuse only while the platform is *reachable*), and `CLAUDE.md` §13
records it as an invariant — but the document that a future contributor would most likely read first
told them to undo it. Corrected, with the reasoning, rather than merely softened.

## Still open — carried forward unchanged

None of these moved, and each needs either a real container or a decision that is not code's to make.
Full detail in [`ACTION_REQUIRED.md`](ACTION_REQUIRED.md) §4:

| | Why it is still open |
|---|---|
| Container runs as root (DONATIONS-015) | Needs `USER node` **plus** an entrypoint that chowns `/data`, **plus** one real container start proving the database is still writable. Shipping it unverified risks bricking every install on update. |
| Base images pinned by tag, not digest (DONATIONS-016) | Mechanical, but a wrong digest fails the build and the workflow does not run on PRs. |
| No Content-Security-Policy (DONATIONS-014) | Must be written against a live Stripe Payment Element in a browser. A slightly wrong CSP stops donors paying, with no obvious error. Highest-value missing header. |
| No session revocation / password change (DONATIONS-013) | An auth-model change (token versioning) with no existing auth-route tests. |
| `/api/setup` during a platform outage (DONATIONS-005) | A deliberate, documented trade — the escape hatch that stops the panel bricking. Recommendation stands: keep the hatch, make abuse loud. |
| Limiters collapse behind the ingress (DONATIONS-009) | Needs a written guarantee from the platform about which forwarded headers its ingress strips. |
| Anonymous donations de-anonymised at confirm (DONATIONS-024) | A product decision: is a blank name "I wish to be anonymous" or "I couldn't be bothered"? |
| Tunnel token visible in the process table (DONATIONS-026) | `cloudflared` is believed to read `TUNNEL_TOKEN` from the environment, but getting it wrong silently breaks public access, and it cannot be tested here. Practical severity is low: reading it needs host access, which already grants the SQLite file. |
