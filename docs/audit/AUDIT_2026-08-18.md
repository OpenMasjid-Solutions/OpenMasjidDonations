# Security and code-health sweep — 2026-08-18 (v0.43.0)

A third pass over the whole app, five days after the [2026-08-13 sweep](AUDIT_2026-08-13.md), and
the first to cover the three features added since it: **WhatsApp notifications**, **admin commands
over WhatsApp**, and **per-event notification settings** — plus the light-mode port from
OpenMasjidStudents. Scope: every server route, the data layer, the notification fan-out, the web
bundle, the container, both dependency trees, every external URL, and all fifteen markdown files.

**Headline:** no new vulnerability, and no defect that has cost a masjid money. What it did find is
**two ways the app tells a masjid something untrue** — one about their monthly donors, one about an
appeal it claims not to have — plus a small unmetered call and four High dependency advisories that
had been argued away twice and are now simply gone.

The two wrong answers matter more than their severity ratings suggest, because both are the kind of
wrong that looks right: nothing errors, nothing logs, and the figure on the screen is confidently
incorrect.

---

## Fixed in this sweep

### D-2026-0818-1 — "monthly donors" counted plans that stopped years ago (Medium, correctness)

`!donations monthly` answered from every recurring row that had ever taken money. **Nothing local
records that a plan ended** — a cancellation happens at Stripe, and a LAN-only masjid may never see
the `charge.refunded`/subscription webhooks at all — so the succeeded rows of a plan canceled two
years ago sit in `donations` looking exactly like a live one's.

The failure grows with the age of the install, which is why five days of testing never showed it. A
masjid three years in, with forty ended plans and ten live ones, was told:

> *50 monthly donors, giving about $2,000 a month.*

when the truth was ten and $400. Confidently wrong, about money, in the flattering direction.

**Fixed** by giving `Store.monthlyGiving` a recency cutoff. A live monthly plan is charged every
month, so "nothing charged in the last two months" is the one signal available locally that a plan
has stopped — and the ones that fail it are returned as `dormant` and *said out loud* rather than
dropped, because a figure that quietly shrank cannot be explained from a phone. Two months rather
than one, so a plan the day before its renewal is not called dormant and a retry after a declined
card has room. Six new tests, four of them against a real database.

### D-2026-0818-2 — an appeal past the twelfth was unanswerable by every route at once (Medium, correctness)

The `appeal` command caps its numbered menu at twelve so one WhatsApp message stays readable. The
cap was applied to the list **before** it was searched, so with thirteen appeals the thirteenth could
not be reached at all: not by number, because it was never printed, and not by name either, because
it was not in the list being matched. The reply was *"Sorry — I didn't recognize that one"* about an
appeal the masjid was looking at in the panel.

**Fixed** by splitting the two: a **number** may only ever index a line that was actually shown, a
**name** is matched against every appeal the masjid has, and the menu now says how many did not fit
(*"…and 3 more — type part of the name for one of those"*) — because an appeal simply missing from a
list reads as one the app has lost. Verified on a booted server with fifteen appeals: `Appeal 15`
answers, and `13` still re-asks rather than silently meaning the thirteenth.

### D-2026-0818-3 — `POST /api/setup` was an unmetered outbound platform call (Low, availability)

Two unauthenticated routes that call the platform on every request are capped at 120/min per peer
for exactly this reason. `/api/setup` is a third and was not.

It matters more than it looks: under SSO the local admin is never set, so `store.hasAdmin()` is
false for the **whole life of every embedded install** and the 409 short-circuit above it never
fires. Every POST therefore reached `probePlatform` → `platformReachable`, one 3-second socket
against the OS core, from anyone who can reach the box.

**Fixed** with the same limiter and the same 429. Verified live: the 121st request in a minute is
refused, including one carrying a valid password. The cap is 120× what a real first run needs, and
the recovery trade-off in `ACTION_REQUIRED.md` §4a is unchanged and still Hasan's to make.

### D-2026-0818-4 — a throttled WhatsApp status probe was cached as a settled "no" (Low, correctness)

`whatsappStatus` cached every non-ok response for 60 seconds with `reason: 'not-allowed'`. A 429 or a
5xx is **no information** — the platform never answered — so one throttled probe turned into a minute
of the panel saying *"OpenMasjidOS isn't allowing this app to send WhatsApp messages"*, sending an
admin to check a permission that was never off, and a minute of `raise()` skipping the WhatsApp leg
of every notification.

**Fixed** by serving the last good answer and not overwriting it. This is the same rule
`fetchFabricStripeDetailed` already follows for the Stripe vault, for the same reason, and
`CLAUDE.md` §13 states it there; it now holds on both paths. A 403 is still cached — *"you do not
hold this capability"* is an answer.

### D-2026-0818-5 — a client 4xx wrote ERROR into the masjid's log (Low, observability)

The error handler logged every thrown error at `error`, including client mistakes. Several are
reachable without signing in — `/uploads/` names a directory and the static plugin refuses it, an
upload over 5 MiB is a 413, an unreadable body is a 400 — so a passer-by on the LAN could fill a
masjid's log with ERROR lines and bury the one that mattered.

**Fixed:** 5xx stays loud, 4xx drops to `debug`. Verified live — two client 4xx requests, zero new
ERROR lines.

### D-2026-0818-6 — four High advisories on `@fastify/static` (High advisory, refuted as exploitable — upgraded anyway)

`@fastify/static` 8.x carries four High advisories: path traversal in directory listing, route-guard
bypass via encoded separators, authorization bypass via non-canonical paths, and route-guard bypass
via traversal. All four were **refuted as exploitable here** in the previous two audits, correctly:
both registrations use `index: false`, neither sets `list: true`, neither sits behind a route guard,
and both roots hold already-public assets.

Deferred twice on that reasoning (`ACTION_REQUIRED.md` §4g). **Done this time**, 8.x → 10.1.3.
Being right about unreachability is not the same as being clean; a fourth advisory had arrived on the
same package; and "we reasoned it was fine" is a worse answer to a masjid than "we upgraded it". Two
majors, but the API surface in use is four options across two registrations, so it is one line in
`package.json`.

Verified by a real container start rather than by the suite alone: the SPA, a hashed asset, an
uploaded image, the SPA fallback for `/admin` and a 401 on an admin route all behave, and five
traversal shapes (`../`, `%2e%2e/`, `..%2f`, `%2e%2e%2f`, `....//`) all return 404 with no file body.
One behavior change: `/uploads/` is now a 403 from the plugin rather than a 404 — see D-5, which is
why it is no longer an ERROR line.

### D-2026-0818-7 — `nanoid` advisory in the web build (Low advisory)

`nanoid < 3.3.18`, reached only through `postcss`, only at build time, and only exploitable through a
custom generator that postcss does not use. A lockfile bump. Both `npm audit` runs are now clean at
zero.

external URLs answer 200. The drift found was all in one place — the three features added in the
last five days:

## Checked and found sound

Not everything worth checking produces a finding. These were examined closely and needed no change:

- **The two-header check on `/fabric/commands/run`.** Verified live: no headers, secret only, and a
  wrong caller id are all a flat 403; both correct is a 200. The app secret never appears in the log.
- **No donor can be named by a command.** Structural, not habitual — no parameter in the reply
  surface could carry a name, email or reference, and `commands.test.ts` fails if one is added.
- **`toWhatsAppDigits` refuses rather than repairs.** A leading zero is a trunk prefix, never a
  country code; a guess would send a masjid's donation figures to whoever holds that number in the
  guessed country.
- **A group id is re-verified against the approved list before it is saved**, not merely
  shape-checked, so withdrawn approval surfaces on the settings screen and not silently at send time.
- **`minAmount` gates every channel of the per-donation event**, on both the confirm path and the
  renewal-webhook path, and deliberately does *not* gate "a donation was found and added".
- **The notification audit line records counts only** — never an address or a number, not even
  masked, because in a small community the last two digits of a phone number still name somebody.
- **CSV injection**, **the SSO setup guard**, **tuition/donation route isolation**, **refund
  monotonicity**, **per-appeal account resolution**, and **the receipt gate** — all six §13 invariant
  families re-read against the code. Intact.
- **No `dangerouslySetInnerHTML`, no `eval`, no `new Function`** anywhere in the web bundle.
- **No Stripe secret, app secret or webhook secret reaches a log line.** Re-grepped.

## Addendum — the release reached the tag, not the masjids (same day)

Raised by the platform side after this report was written, and worth recording because two of the
three points were real gaps in the runbook rather than in the code.

**A tag is not a release.** This repo had eight tags and **zero published GitHub releases**. Nothing
in §16.1 asked for one, so nobody ever made one, and every release's notes were unreadable to the
admin they were written for. `v0.43.0`'s release is now published; §16.1 grew a step 5.

**A release is not a catalogue entry.** Masjids install from
`OpenMasjidAPPS/main/catalog.json`, which still reported 0.42.0 (with the old five-alert manifest)
while this repo sat at 0.43.0. The PR against the catalogue's `dev` was opened as part of the
release (`OpenMasjidAPPS#25`, green and mergeable) — that step was not skipped — but the stable
column moves only when a catalogue maintainer releases it, which is deliberately not ours. §16.1
grew a step 7: check the live `catalog.json`, because it is the only thing that answers *"did it
ship?"*, and expect to have to ask for it.

**`commit:` is the commit sha, not the tag object's.** Checked: the entry pins `298702f…`
(`git rev-parse v0.43.0^{commit}`), not `2a1f947…` (the annotated tag object, which is what
`gh api …/git/ref/tags/…` returns and what would have made the catalogue build 404).

### The tag/pin digest divergence, diagnosed

The one technical question asked — why `:0.43.0` moved off the pinned digest, and whether a
Raspberry Pi is therefore running different code — is answered in `CLAUDE.md` §16.1 in full. The
short version, from fetching and comparing both configs blob by blob:

- **amd64:** the two indexes name the *same* manifest. Identical.
- **arm64:** different manifest digests, but **all twelve layer digests, `rootfs.diff_ids`, the
  runtime config and the top-level `created` are identical.** The sole difference is
  `history[13].created` — **2.5 milliseconds** apart.

So the filesystem a Pi runs is byte-for-byte the same under either digest; nothing was fixed on ARM
by the re-push, and nothing is missing from the pinned build. The cause was `build-image.yml`
triggering on `tags: ['v*']`, so pushing the tag rebuilt from cache and republished; that trigger is
removed. Making the two agree for v0.43.0 needs a **retag** (a rebuild would produce a third
digest), which needs a `write:packages` token that the gh CLI's default scopes do not carry — the
exact command is in §16.1 for whoever holds one.
